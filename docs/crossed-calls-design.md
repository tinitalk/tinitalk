# Встречные звонки

## Цель

Если два свободных абонента одновременно звонят друг другу, сервер сводит попытки в один активный звонок. Оба клиента переходят с экрана дозвона на экран разговора без ручного ответа. Звонок третьему абоненту и звонок уже разговаривающему абоненту по-прежнему завершаются состоянием «Занято».

## Границы сценария

Сведение разрешено только для точной встречной пары:

- на сервере уже существует ожидающий звонок `А → Б`;
- `Б` отправляет `call.start` именно для `А`;
- существующий звонок ещё не принят и не завершён;
- оба клиента объявили поддержку встречных звонков.

Сервер не объединяет звонки с третьими абонентами и не изменяет активный разговор.

## Совместимость

Обновлённый Android-клиент добавляет в `call.start` поле `supports_cross_call: true`. Старый сервер проигнорирует неизвестное поле. Обновлённый сервер выполняет сведение, только если это поле было получено от обоих участников; с остальными клиентами сохраняется обычный ответ `busy`.

Это позволяет обновлять сервер и телефоны в любом порядке.

## Серверная модель

Идентификатор ожидающего звонка `А → Б` становится каноническим. Идентификатор встречной попытки `Б → А` не создаёт второй серверный звонок.

При точном совпадении сервер под общей блокировкой:

1. запоминает идентификатор события встречного `call.start` для идемпотентности;
2. переводит канонический звонок в активное состояние;
3. отправляет исходному вызывающему `call.accept` с `crossed: true` и `offerer: true`;
4. отправляет встречному вызывающему `call.accept` с `crossed: true` и `offerer: false`;
5. выдаёт обоим участникам ICE-конфигурацию;
6. отменяет ожидающее входящее уведомление канонического звонка.

Роли канонического звонка не меняются: исходный вызывающий создаёт WebRTC offer, исходный вызываемый создаёт answer. Поэтому одновременное создание двух offer невозможно.

Повторная доставка того же встречного `call.start` ничего не меняет. Replay и `call.resume` работают по каноническому идентификатору.

## Ошибки сигналинга

Сервер добавляет `call_id` во все ответы с ошибкой, относящиеся к входному событию. Android завершает текущий звонок только при ошибке с его каноническим `call_id` либо при некоррелированной ошибке соединения.

Ошибки от отброшенного идентификатора встречной попытки игнорируются. Это необходимо для запоздавших `call.resume` и `call.cancel`, которые могли попасть в очередь до получения `call.accept`.

## Android-состояние

`CallCoordinator` принимает канонический `call_id` из встречного `call.accept` и переводит локальный звонок в `Active`.

`ForegroundCallController` учитывает поле `offerer`:

- отсутствие поля сохраняет текущее поведение обычного звонка;
- `offerer: true` запускает создание offer после получения ICE-конфигурации;
- `offerer: false` ожидает offer и отвечает на него.

Сервис сохраняет отдельно:

- канонический идентификатор сигналинга;
- локальный идентификатор уже созданной Telecom-сессии;
- имя и логин выбранного собеседника.

При сведении второго клиента UI заново публикуется как исходящий активный звонок с прежним собеседником и каноническим идентификатором. Локальная Telecom-сессия не пересоздаётся: её идентификатор используется для `setActive`, выбора аудиомаршрута, системных callbacks и завершения.

Запоздавшее входящее уведомление канонического звонка помечается обработанным и скрывается. Если Android уже успел создать лишнюю входящую Telecom-сессию, она отключается; её callback считается устаревшим и не завершает активный разговор.

## Завершение и восстановление

После сведения `call.end`, ICE-события и переподключение WSS используют только канонический идентификатор. Отключение локальной Telecom-сессии завершает канонический звонок. При повторном подключении клиент отправляет `call.resume` для канонического звонка и получает обычный replay.

Если встречная попытка не удовлетворяет условиям сведения, сервер возвращает `busy`, и существующий сценарий «Занято» остаётся без изменений.

## Проверки

- Серверный тест подтверждает сведение точной встречной пары, единственный активный звонок, назначение ролей и выдачу ICE-конфигурации.
- Серверный тест подтверждает `busy` для третьего абонента, активного разговора и клиента без поддержки возможности.
- Android-тест подтверждает принятие канонического идентификатора.
- Android-тест подтверждает, что offer создаёт только назначенный участник.
- Android-тест подтверждает игнорирование ошибки отброшенного идентификатора.
- Android-тест подтверждает разделение канонического и локального Telecom-идентификаторов.
- Выполняются полные тесты Go, Android unit tests и сборка обоих артефактов.

Финальная проверка проводится на двух физических телефонах: одновременный вызов, автоматический переход в разговор, звук в обе стороны, завершение с каждого телефона и отсутствие лишнего входящего уведомления.
